# 实验三 负载与压力测试答辩补充

成员：温家正、姚景云、杜奕含、陈浩贤  
对应：16 页《MySQL读写性能测试报告》修订版。页码指 PDF 页码。

## 开场怎么说

我们用 JMeter 测试商品查询和新建接口，在不同负载下比较响应时间、吞吐量和错误率，并用 Prometheus 观察线程、CPU 和内存。测量对象是完整接口链路，不是单独一条 MySQL 语句。

## 1．负载测试与压力测试有什么区别？我们属于哪一种？

**对应报告第 1～2、15 页。**

- **负载测试**：观察系统在不同负载、通常是预期使用范围内的表现。
- **压力测试**：观察超出正常负载范围或资源受限时，系统如何退化、出错及恢复。
- **我们的报告**主要是不同负载配置下的性能比较。虽然出现过高延迟，但还没有证明稳定的容量上限，也没有完成系统性的超载与恢复验证。

不能把“用了 JMeter”或“线程数很大”直接当作完成压力测试的证据。

## 2．1000-10-2 是什么意思？等于 2000 并发吗？

**对应报告第 2～3、15 页。**

表示 1000 个 JMeter 线程、10 秒内逐步启动、每个循环 2 次。本计划每循环一个请求，所以预期共 2000 次请求，**不是同时有 2000 个请求**。

线程数决定模拟用户规模，升压时间影响启动集中程度，循环次数影响工作量和线程持续时间。10 秒也不是整场测试必须结束的时间。

## 3．为什么选这些档位？另一组做到 5000，我们不够吗？

**对应报告第 2、15 页。**

我们沿用参考样例的读取 1000～1200、写入 1000～1300 档位，统一升压时间做比较。指导书没有规定必须达到 5000，但我们的负载范围确实较窄，不能据此声称测出了最大承载能力。

比较不同组前，要核对接口、升压、循环、配置和实际吞吐量，不能只比线程数。

## 4．怎么从图上判断性能退化？

**对应报告第 3～11 页。**

看负载增加后，**响应时间尤其 P95/P99 是否升高、吞吐量是否趋于停滞、错误是否增加**。时间趋势图看何时变慢，百分位图看慢请求的分布。

错误率为 0 只说明既定断言通过，不代表性能达标。CPU 高或线程多也不能单独证明某个组件是瓶颈。

## 5．为什么用“80% 在 40 ms 内”？和 P95 有什么区别？

**对应报告第 2、11 页。**

这是沿用样例的自选比较条件，不是指导书的统一验收指标。我们计算的是 **success=true 且 elapsed≤40 ms 的请求比例**，要求不低于 80%。P95≤40 ms 是另一种、更严格的延迟条件。

例如第一轮 MyBatis 写 1300：错误率为 0，但 40 ms 内成功比例只有 **71.77%**，所以没有达到本组比较条件。

## 6．1300 线程写入变慢，能说系统极限是 1200 吗？

**对应报告第 11～13 页。**

不能。MyBatis 写 1300 的三轮平均响应分别为 **102.03、6.76、6.05 ms**，第一轮尖峰没有稳定复现；其他低档位也有异常。

因此只能说“该轮出现延迟退化”。判断稳定边界需要固定环境、重复测量，并在退化区域细分负载。

## 7．JMeter 线程增加，为什么 JVM 线程可能不变？

**对应报告第 14～15 页。**

JMeter 线程在压测端；JVM 指标统计后端存活线程，包含空闲和等待线程。后端会复用线程池，已有线程够用时，总数可以不变。

老师原配置最少保留 **100** 个 Tomcat 工作线程，当前部署最大为 **300**。报告中的 **115→124** 对应第一轮 MyBatis 写 1300；同批其他 MyBatis 记录多数保持 124，并非每次改参数都会上涨。

另外，原始指标约每 **2 秒**采集，带 `spring:` 的规则每 **30 秒**记录，可能看不到短暂变化；CPU 的 **5 分钟**窗口也会平滑短时峰值。

## 8．怎么保证比较公平？为什么要做三轮？

**对应报告第 2、12～13 页。**

固定接口、数据基线、应用资源、预热、升压及循环设置，每次保存独立记录。重复测试用于判断结果是否稳定，异常轮次也要保留。

本报告读循环 2 次、写循环 1 次，不能将吞吐量差别完全归因于读写实现。第二、三轮缺少每组完整环境快照，能说明波动，不能证明条件完全一致。

## 9．如果继续做压力测试，怎么设计？

**对应报告第 15～16 页。以下是后续方案，不是已完成结果。**

1. 固定环境和数据，先采集空闲与低负载基线。
2. 逐级增加持续负载，一次只改一个参数，保留稳定运行阶段。
3. 同时记录实际活跃线程、吞吐量、P95/P99、错误率及各服务器资源。
4. 在明显退化区域重复测试，停止加压后检查响应、错误率和服务状态是否恢复。

还要检查压测机是否先达到瓶颈。不能把吞吐量停滞直接认定为 MySQL 极限，也不能把 JVM 扩到 300 个工作线程等同于系统最大承载能力。

## 最后记住三句话

- **配置线程数不等于同时在途请求数。**
- **请求成功不等于响应时间达标。**
- **一次退化不等于测出了稳定极限。**
