# 实验三要求核查

核查日期：2026-10-23。依据本组原报告、实验指导书、参考样例、另一组报告，以及 CDWY3 保存的原始记录。

## 数据是否符合要求

已覆盖要求的两个 API：商品查询 GET `/shops/{shopId}/products/{id}` 与新建 POST `/shops/1/products`；已有 JMeter JTL、趋势图、百分位图，以及 JVM 活跃线程、CPU、内存三项 Prometheus 记录。第一轮18组的均值、样本数、吞吐量与 JMeter HTML 报告一致，原有分析脚本还核对了监控元数据中的数据库行数。三轮54组、93600条样本全部通过原有断言。

这些证据能够支持已完成读写性能采集与比较。不能仅据此承诺教师最终验收通过：指导书要求程序和原始数据得到教师认可、报告论证严谨。读取负载上限没有测到；写入尖峰未稳定复现，当前尚不足以给出稳定容量或确定瓶颈归因。

## 为什么另一组做到5000线程

指导书没有规定最低5000线程；给出的运行示例是1000线程、10秒升压、1次循环。另一组扩展了线程档位，读测试覆盖5000～7000，目的是探索退化区域。本组先使用样例的1000～1200读取和1000～1300写入档位，负载探索范围较窄。

5000线程、10秒升压、1次循环，是逐步启动5000个线程；在没有额外采样器时共5000次请求，不表示5000个请求同时在途，也不保证全部请求在10秒内完成。另一组报告的5000线程读测吞吐量约508次/s；本组第一轮MyBatis读取约203～254次/s，且本组读取循环为2次，不能只对比线程数。

原样例采用“80%请求在40ms内”，另一组采用“P95≤40ms”。二者评价标准不同；本组保持原样例80%标准，同时报告P95。另一组写测试5000线程的表列P95为70ms，因此若使用其自身P95≤40ms标准，这一档不能写作达标。另一组的描述和判断也不能直接照抄。

按参考的论文结构与图片形式整理中英文题目、四名成员、摘要、关键词、编号章节、三线表、原生JMeter截图和Prometheus历史截图。第一轮逐档原图不变；新增三轮对照使用服务器已有JTL，全部保留高延迟轮次。新报告不再把1300线程称为固定上限，也不把既定断言成功等同于延迟达标。

## 如需进一步完善

后续应统一并记录预热、数据基线、冷却过程和后台进程状态，延长稳态采集；逐步提高读负载并在退化区域重复细分。监控需同时覆盖压测机、应用和数据库。当前CPU规则使用5分钟窗口、记录规则30秒更新，而单组测试约十余秒，因此旧监控不足以定位短时延迟尖峰。此次未重跑压力测试、未修改任何服务器配置。
